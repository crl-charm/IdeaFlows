# Receivables by date, search, and fresh customer debt tabs

**Status:** Implemented locally. The new schema and legacy backfill have not been run on the live VPS. Back up the live database and verify row counts and money totals before applying the migration there.

## Goal and confirmed rules

“Utang” here means **money the customer owes the business**. The owner needs to choose a date and see only the debt created by customers for items taken on that date, while retaining a clear **Show All Utang** view and an all-date outstanding total. Admin and staff must have the same date/search behavior on their existing Receivables pages.

- Filter by `Receivable.incurred_date` (**Date Taken / Incurred**), even if staff entered the record on a later date. Payment date and due date do not move the debt to another Date Taken view.
- Match customers by normalized name **and** contact. The same name with different contact numbers is separate. Do not silently merge two people who share a name.
- A customer tab exists only while that debt cycle has an unpaid balance. When the last balance is paid, the tab disappears from active Customer tabs but all debt and payment records stay in history.
- If the same person borrows again after fully settling, open a **new tab/cycle**. Prior paid orders belong only to history/date views and must not inflate the new tab's orders total, payment history, or balance.
- A selected date shows only customers with a debt taken on that date in the date-filtered Customer tabs section. **Show All Utang** removes the date filter and shows all dates. The all-date outstanding total remains visible even with a date selected.

## Existing behavior and code

- `app/models/receivable.py` has one `Receivable` per debt/order with `items_description`, `amount_owed`, `partial_paid`, `paid`, `incurred_date`, `due_date`, `created_at`, actor, and optional session. `ReceivablePayment` stores payment method, received time/actor, amount, before/after balance, payment group, and retry key.
- `app/repositories/receivable_repository.py` already supports paginated status/search results, but has no date filter or persistent customer tab ID. Its customer payment allocates oldest unpaid debts matching normalized name and contact.
- `app/services/receivable_service.py` serializes Date Taken, creates debts, records payments under the Daily Balance method/day lock, and exposes grouped payment history.
- Admin routes/UI: `app/routes/receivables.py`, `app/templates/admin/receivables.html`. Staff routes/UI: `app/routes/staff_receivables.py`, `app/templates/staff/receivables.html`. Both pages currently fetch **all** records and build tabs in browser JS by name/contact. Paid customers remain in the admin list and in the staff Customer tabs table; a later debt reuses old paid rows in that grouping.
- `app/utils/dates.py` defines Manila business-day helpers. `app/repositories/sales_repository.py` already places receivable collections into Daily Balance by **payment date and method**. This plan must not change that rule.

## Screen behavior

1. Put a labelled Date Taken picker, **Today**, and **Show All Utang** above the records on both admin and staff pages. Default the picker to the current **Asia/Manila** date. The selected date remains visible in the heading and URL query so refresh/back navigation preserves it. Show All clears the filter and visibly marks the all-date mode.
2. Add a search input for customer name, contact, and items description. Search combines with the selected date and existing paid/unpaid status where offered. Debounce requests; ignore a stale earlier response after the date/search changes. Provide a clear-search control and empty/loading/error states.
3. The dated **Receivable Records / Date Taken** list shows each debt from that date, including debts since paid in full, with customer, contact, items, notes, original amount, amount paid, remaining amount, Date Taken, due date, and status. Historical paid records stay readable; they do not reappear as active tabs. Pagination must let staff reach older/long lists.
4. Show two amounts with unambiguous labels: **All dates still owed** is the current outstanding balance across every debt, and **Selected date: debt taken / still owed** applies only to debt incurred on that date. Neither amount is a payment received today. Show All may replace the second with an all-date original-debt figure. Count active customer tabs separately from debt rows.
5. Customer tabs list only **open** debt cycles. Under a selected date, include an open tab only if it contains a debt with that Date Taken; Show All lists all open tabs. A row shows the amount taken on the selected date separately from the tab's **all-date outstanding** balance. This prevents a date filter from implying that an all-date payment is only paying that date's debt.
6. Opening a tab shows its current cycle's orders and payment history, separated or labelled by Date Taken. A payment form clearly says it applies to the **whole open tab**, oldest unpaid order first, and displays the whole-tab balance before submitting. The date filter does not alter payment allocation. If the owner wants date-specific payment allocation later, that is a separate behavior change.
7. In Add Receivable, suggest only **currently open** tabs matching the typed name and contact. Choosing one fills and locks its identity (or displays the chosen tab explicitly) and adds a new debt to it. After a tab is fully settled it is absent from suggestions; a new entry for that same person creates a fresh tab. With a blank contact and a name shared by multiple people, require the staff member to select the intended open tab explicitly or create a new one; never auto-merge solely on the name. Keep the staff-entered Date Taken editable and visible before save.

Example: Ana takes ₱100 of rice on September 29 and ₱80 of eggs on September 30. September 29 shows only the rice debt; September 30 shows only the eggs debt; Show All shows both. The open tab balance is ₱180 until collections reduce it. If Ana pays ₱180 on October 1, her active tab disappears, both dated debt records and the October 1 payment history remain, and Daily Balance records the ₱180 collection on October 1 by payment method. If she borrows again on October 2, that debt starts a new active tab with no old paid orders folded into its total.

## Persistent tab identity and migration

Current name/contact grouping cannot distinguish a newly reopened tab from a fully paid old one. Add a small persistent debt-cycle identity rather than relying on display names or `payment_group_id` (which identifies one payment event). A `receivable_tabs` row with an ID, normalized name/contact, opening time, optional closing time, and an active identity key, plus `receivables.tab_id`, is sufficient. Use a unique active identity key (nullable once closed) or an equivalent database-enforced guard so concurrent creates cannot open two active tabs for one **nonblank** name/contact pair. For blank contacts, leave that key null and require explicit tab selection to join an existing open tab; the same name alone must not force a merge. Keep all amounts on `receivables` and `receivable_payments`; do not introduce a second financial ledger.

- On create, in one transaction, find and lock the matching open tab or create one; attach the new receivable. A selected tab ID must be open and match the submitted identity. Ensure a retry of Create cannot make a second debt or tab; keep the existing idempotency behavior.
- On a customer payment, lock the open tab and its unpaid debts, allocate in stable Date Taken/ID order, write the existing per-debt payment rows with amount, method, actor, time and before/after balance, and close the tab **in the same transaction** when its remaining balance becomes zero. Per-record payment endpoints must close the tab when they settle its last debt too. Concurrent create/payment must have a consistent lock order and cannot attach debt to a closed tab.
- Change the tab payment/detail APIs to target `tab_id` rather than a client-provided name/contact. Keep the existing name/contact fields as display/search data. Do not let a selected-date view accidentally pay another customer or another paid cycle.
- Migrate existing unpaid rows into one open tab per normalized name+contact. Preserve existing paid rows as historical closed/legacy cycles; old overlapping debt cycles may be impossible to reconstruct exactly, so do not invent a single old balance or rewrite any payment. Backfill missing Date Taken with the **Manila date** of `created_at` where possible, recording the migration separately. Make migration idempotent and check live counts/sums before and after: total original owed, total payments, and current outstanding must not change.
- Index `receivables(tab_id, incurred_date, id)` and the active identity key, and keep the payment indexes. Retain paid rows indefinitely under the existing retention policy. The daily money ledger remains based on `ReceivablePayment.received_at`, never on `incurred_date` or tab close time.

## Read APIs and query rules

- Extend the existing paginated GET endpoints under `/admin/receivables/api/receivables` and `/receivables-view/api/receivables` with optional `date=YYYY-MM-DD`, `search`, `status`, `page`, and bounded `per_page`. No date means Show All. Validate exact ISO date and reject invalid pagination/status; search with bound SQL parameters and escape displayed text. Sort Date Taken descending, then ID descending.
- Add one shared repository/service query for active tab summaries, exposed under each role's existing Receivables prefix (for example `/api/receivables/tabs`). It applies the optional date/search to **which tab rows appear**, but computes each tab's full-cycle outstanding from all its debts. Derive date-specific amounts separately. Do not group a paginated debt page in JavaScript; a tab spanning pages would otherwise have the wrong balance.
- Return all-date outstanding from an aggregate query independent of the current records page. A selected-date aggregate must use `incurred_date`, not `created_at`/`due_date`/`received_at`. Reuse server-side predicates for admin/staff so counts, search and rows agree. If old null incurred dates remain before migration, use `manila_date(created_at)` as a documented fallback rather than UTC `.date()`.
- Keep all mutating routes authenticated and CSRF/idempotency protected. Staff must keep using `/receivables-view/...` and must not need Cloudflare-protected `/admin/...` URLs. Preserve admin and staff action permissions already agreed for Receivables.

Verify live cards, generated report and exports agree for the same Manila day.

Inspect the diff for duplicated admin/staff logic, schema migration safety, and accessible desktop/mobile UI. Before applying the migration on live data, take a verified database backup and check row/amount counts; this plan is not authorization to reset or delete live records.

**Done when:** each date shows exactly the debts taken that day, Show All and search remain usable for long history, the all-date outstanding amount stays visible, fully paid tabs disappear without losing history, and a new borrowing after settlement starts a clean tab whose payments reconcile with Daily Balance.
